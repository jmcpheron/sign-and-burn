# 2026-10-10: QR codes, and a compact approval

## The ask

Share each link with an optional QR code. Two choices were put to Jason, and he chose: write the
encoder here rather than add a package, and design a compact approval so a signed approval fits one
code too.

## What changed

- **`site/src/qr.mjs`**, a QR encoder written here: byte and alphanumeric modes, mixed in one code,
  versions 1 to 40, all four error correction levels, the eight masks scored as ISO 18004 says. Its
  structure and tables follow Project Nayuki's QR Code generator (MIT), credited in NOTICE.
- **"Show QR code"** beside each "Copy link": the build link (two places on the main page), a signed
  approval (both pages), and a transaction for another owner (the wallet page). The wallet page also
  shows the seat's address as a code, for adding it to a Safe on another device. Codes are black on
  white whatever the theme, with the four-module quiet zone, and stay open across redraws.
- **The compact approval**, `sign-and-burn/approval-qr/v1` (`#aq=`, `src/pay.mjs`). The approval link
  is about 3,600 characters; the largest QR code holds 2,953 bytes. Most of it is the one-time
  signature, 67 values of 32 bytes, which can't be shortened. The compact form packs the same fields as
  bytes and the curve signature as its four parts (about 2,440 bytes). It writes them in base 43: the
  QR alphanumeric set without space and `%`, which a URL would escape. That is 5.5 bits a character
  in the code, and nothing a URL fragment escapes. About 3,750 characters, a version 37 or 38 code. A
  page that opens it gets exactly what the approval link gives, and checks it the same way. The
  approval link itself is unchanged; the compact form is only in the code.

The console is unchanged, so its fingerprint is too. The contracts are unchanged.

## What was checked, and how

- **Module for module against an independent encoder.** python-qrcode 8.2, in a throwaway virtual
  environment, made 16 codes (`tools/qr-vectors.py` → `site/qr-vectors.json`): versions 1 to 37, all
  four levels, byte, alphanumeric, and the two mixed, each with its mask fixed. `npm test` checks
  `qr.mjs` draws each one bit for bit. The masks are fixed because encoders score them a little
  differently: in 3 of 7 cases ours chose another mask than python-qrcode did. Any mask is valid;
  the code says which one it used.
- **Decoded.** OpenCV 5.0's QR decoder (`QRCodeDetectorAruco`, same throwaway environment) read our
  codes back to their text: versions 2, 3 and 37 drawn from `qr.mjs` directly. It also read the e2e's
  screenshot of the approval's code as Chromium drew it, to the compact link, in 16 of 20 sizes and
  scalings. OpenCV's other decoder (`QRCodeDetector`) read neither ours nor python-qrcode's at
  version 37: it is a limit of that decoder.
- `npm test`: a compact approval reads as the approval link does, fits one code, is refused one
  character short, one byte long, with a character outside base 43, or for another chain; a curve
  signature that isn't canonical gets no compact form.
- `npm run e2e`: all 124 checks pass. New: the build link's QR code holds the link; the approval's
  code holds its compact form; the second browser opens that link and gets the same approval, the same
  check code, and the seat's acceptance.

Not checked: a real phone's camera on a real screen. A version 38 code is dense (169 modules a side).
On a laptop screen it is about 3.5 pixels a module, and phone cameras usually read that, but it
hasn't been tried. It may need to be shown larger, or split across two codes in a later format.

## Found along the way

- The first decode of the browser's screenshot failed: Chromium shrank the 708-pixel canvas to 633
  with pixelated scaling, so the modules came out 3 or 4 pixels wide. The same image decoded at its own
  size by another path, and at most other sizes. It is noted for the phone test.
