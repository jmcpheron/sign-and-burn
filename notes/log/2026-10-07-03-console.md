## The design

Not a 240 × 240 screen any more: the page draws a full-size console in HTML. The console's code became
a core with no screen at all: `core.handle(line)`, one JSON request in, one answer out. In the browser,
the page calls it. On a board, `main.py` reads the same lines from USB serial. That is what makes "could
run on an ESP32" a claim with a test behind it.

The core builds `c` and `m` itself, checks the passkey's answer, signs with the one-time key, and keeps
the guardrail in `ledger.json`, written before any signature leaves it.

## MicroPython 1.26 for WebAssembly

- It has `hashlib.sha256` in C: 2,000 hashes took 4 ms. So the one-time keys run in the console itself.
- `decode.py`'s vectors are Base mainnet transactions naming Base's USDC and Uniswap's router; the
  console's config pins Base Sepolia only, so the check adds those two as a fixture.

## The heap: 661 KB, then 33 KB

The first measurement said the loaded console held 661 KB, far more than an ESP32 has. Module by module,
`safe_tx.py` alone took 610 KB, and each keccak seemed to keep 200 KB alive. The cause: MicroPython's
WebAssembly port frees garbage only between top-level calls, when no Python frame is on the stack, so a
`gc.collect()` inside the same call frees almost nothing. Collected between calls, the loaded console
holds 33 KB. A board's collector scans its own stack and runs any time.

PicoQuorum's ESP32 notes say MicroPython starts with a 56 KB heap on a WROOM-32 and grows it from what
is left. The page quotes that, not a guess.

## Tests

`console/test/run.py` (CPython) and `run-micropython.mjs` (MicroPython 1.26) run the same checks: 17
Safe-hash vectors, 15 decode expectations, a real browser passkey's assertion that Safe's signer
accepted on chain, and every request and refusal. On MicroPython, `main.py` answered three requests fed
