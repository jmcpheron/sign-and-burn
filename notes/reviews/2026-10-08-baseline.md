## The job's description

This is what gets pasted on onedollaraudit.com. It is public and stored on chain.

```
Sign and Burn contracts, Solidity 0.8.28, no libraries. Testnet demo, not for real money.

Source (please review these three files at this commit):
https://github.com/jmcpheron/sign-and-burn/tree/f5c1c7d07c8b4a3e58f0ed98f8c632ab14da1db2/contracts/src
- Seat.sol, OneTimeKey.sol, SeatFactory.sol
Design, with every message's bytes:
https://github.com/jmcpheron/sign-and-burn/blob/f5c1c7d07c8b4a3e58f0ed98f8c632ab14da1db2/KICKOFF.md
Deployed on Base Sepolia: SeatFactory 0x0a6514135d34dfd19c3f1a636f3e952caeba3871 (via the CREATE2 deployer, salt 0; not verified on Basescan).

What it does: a Seat is one owner of a Safe 1.4.1. Seat.approve(safe, safeTxHash, nextKey, oneTime[67], curveSig) calls safe.approveHash(safeTxHash) only if both signatures check:
- a P-256 passkey signature over c, checked through ERC-1271 by Safe's SafeWebAuthnSignerProxy (safe-modules passkey 0.2.1);
- a Winternitz one-time signature (w=16, 64+3 chains of 15 SHA-256 steps, WOTS+-style tweaks) over m.
c = sha256("sign-and-burn/approve/v1" || chainid || seat || safe || n || safeTxHash), m = sha256("sign-and-burn/one-time/v1" || c || nextKey). n comes from storage. Each approval replaces the current key's fingerprint with nextKey, so every key signs once. No admin, upgrade or recovery.

How it is sent (the page, not these contracts): one Multicall3 aggregate3 call, seat.approve with allowFailure false, then safe.execTransaction with allowFailure true. So a Safe transaction that can't run yet still burns the key and leaves the seat's vote in approvedHashes, for anyone to run later. This is deliberate: key n may only ever send that one approval, so tying the burn to execution could block the seat forever. Why: https://github.com/jmcpheron/sign-and-burn/blob/f5c1c7d07c8b4a3e58f0ed98f8c632ab14da1db2/notes/concepts/one-press.md

Please focus on:
1. Binding: can an approval be replayed on another chain, seat, Safe or n, or redirected to another nextKey? Known gap: the curve signature covers c, not nextKey, so only the one-time signature binds the next key.
2. OneTimeKey: the checksum, digit extraction, chain steps and tweaks; off-by-one errors; any way to forge or to make two messages share a signature.
3. The external call to safe.approveHash after state changes: reentrancy, and what a revert leaves behind. Also the standing vote: an approved hash that can't run yet stays in approvedHashes until it runs or another transaction uses its Safe nonce. Is a burn that doesn't wait for execution safe, in a 1-of-1 and in a real threshold?
4. SeatFactory: CREATE2 seat addresses (firstKey is in the salt); anyone may create seats for any passkey, so seatsOf can hold seats nobody can sign for, or grow without bound.
5. Anything else that lets one key approve twice or lets anyone but the key holder move the seat.
```

## Since the draft (2026-10-10)

- The contracts are unchanged since `f6dd324b`, so the commit above still stands.
- The description now says how a press is sent, and asks about the standing vote
  ([research.md, question 2](../research.md#2-retirement-and-execution)). The reviewer sees only the
  contracts, and the burn not waiting for execution is a choice the page makes.
- A first look at prior art ([research.md, question 7](../research.md#7-prior-art-and-review)) found
  the same choice elsewhere: Riva Labs' Ephemeral Keys rotates during validation, so the rotation
  stands even if execution reverts. wedgie-pq, the nearest design, has no contract yet, so there is
  nothing of it to put in this job. Where the designs differ off chain (a ledger against a chip's
  counter, SHA-256 against Poseidon2, two signatures against one) is a question for a cryptographer,
  not for this review.
- One Dollar Audit is LeftClaw Services' pipeline, and its sample report lives in the same GitHub
  account as wedgie-pq (`clawdbotatg`). That is fine for a first pass, but this review isn't
  independent of a design it may be compared with.
